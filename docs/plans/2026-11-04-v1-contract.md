## Auth e RLS

- Frontend autentica no Supabase Auth (`signInWithPassword`, `signUp`, `resetPasswordForEmail`, `updateUser`); a sessão fornece o access token.
- Flask valida o Bearer em `GET {SUPABASE_URL}/auth/v1/user` com a anon key; toda leitura/escrita normal usa `apikey: SUPABASE_ANON_KEY` + `Authorization: Bearer <jwt>` no PostgREST. O RLS decide.
- O backend nunca aceita `family_id` do cliente. `member_id` só pode ser `auth.uid()` (transações pessoais, contribuições, mensagens pessoais). `pago_por` é a exceção D7 (escopo família).
- Service role só em Admin API (invite) e sync Pluggy; a sync valida antes que a conexão é do usuário. Restore usa `SUPABASE_DB_URL` (pooler 6543). Nenhuma credencial no repo.
- `SupabaseRest` envia `Prefer: return=representation` em POST/PATCH/DELETE; 0 linhas por RLS → 403/404, nunca 204 “sucesso”. Erros `{error:{code,message,details?}}`.
- `GET /api/health` é público. `GET /me` devolve `profile:null` quando o usuário ainda não tem perfil.

## Endpoints

### Identidade e convite

- `GET /api/health` → `{ok:true}`.
- `GET /me` → `{user:{id,email}, profile:{id,family_id,nome,papel,status,tema}|null, family:{id,nome,is_demo}|null}`.
- `PATCH /me` `{nome?,tema?}` → perfil atualizado (RLS/trigger).
- `POST /onboarding` `{nome_familia,nome}` → RPC `onboard_family` (idempotente; perfil existente devolve o mesmo; nomes vazios 422; 12 categorias pela trigger).
- `GET /invites/mine` → convite pendente do e-mail do JWT (`{invite_id,family_id,family_nome,nome,token}` ou `null`).
- `POST /invites/accept` `{token,nome?}` → RPC `accept_invite`; cria perfil membro; 409 se já tem perfil.
- `GET /admin/invites`; `POST /admin/invites` `{email,nome}` (admin) → Admin API `POST /auth/v1/invite` + linha em `invites`; se a linha falhar, compensa/cancela; 503 sem service role; devolve `{invite_id,token,email}`; `DELETE /admin/invites/{id}` cancela.
- `POST /auth/v1/recover` é chamado pelo frontend com a anon key (recuperar senha); a nova senha usa `supabase.auth.updateUser({password})`. O admin não define senha.

### Painel e individual

- `GET /dashboard?mes=YYYY-MM-01` → `{mes, totais:{receitas,despesas,saldo}, acumulado:{receitas,despesas}, categorias:[{category_id,categoria,total}], serie:[{mes,receitas,despesas}], membros:[{member_id,nome,papel}], metas:[...], sugestoes:[...], alertas:[...], recorrentes_pendentes:[...], banco:{conexoes_ativas,pendentes}}`.
- `GET /me/summary?mes=...` → `{mes, totais, categorias, metas, recorrentes_pendentes, sugestoes, alertas, banco:{conexoes,pendentes,ultima_sync}}`.
- `GET /alerts?mes=...` → `{alertas:[{tipo,titulo,detalhe,escopo,member_id?}]}`; sem persistência.
- Dashboard e `/me/summary` chamam o **mesmo serviço de materialização** de ocorrências pendentes de `/recurring/pending`.

### Lançamentos

- `GET /transactions?mes=&tipo=&escopo=&categoria=&origem=&limit=&offset=` → `{items:[{id,tipo,escopo,valor,descricao,category_id,categoria,data,pago_por,pago_por_nome,recurring_rule_id,mes_referencia,origem,bank_transaction_id,criado_por,criado_em}],total}`.
- `POST /transactions` `{tipo,escopo,valor,descricao?,category_id,data,pago_por?}` → **manual apenas**; sem `recurring_rule_id`, `mes_referencia`, `origem` ou `bank_transaction_id`. Importação Pluggy só via `/banking/import`.
- `PATCH /transactions/{id}` campos editáveis; `DELETE /transactions/{id}`; 0 linhas → 403/404.

### Recorrentes

- `GET /recurring/rules?escopo=`; `POST /recurring/rules`; `PATCH /recurring/rules/{id}`; sem DELETE.
- `GET /recurring/pending?mes=YYYY-MM-01`:
  - materializa `recurring_occurrences` pendentes para regras ativas visíveis do mês, idempotente (`on_conflict=rule_id,mes_referencia`, `resolution=ignore-duplicates`), **sem** `merge-duplicates`;
  - depois **relê** todas as `pendente` do mês (não confia no retorno do insert);
  - devolve `{occurrence_id,rule_id,tipo,escopo,valor,descricao,category_id,data_vencimento,dias_para_vencimento}`.
- `POST /recurring/occurrences/{id}/confirm` `{valor?}` → RPC `confirm_occurrence` (atômica; sem compensação destrutiva; 409/42501 se já decidida).
- `POST /recurring/occurrences/{id}/ignore` → status `ignorado`.

### Metas

- `GET /goals?escopo=`; `POST /goals` `{titulo,valor_alvo,prazo?,descricao?,member_id?}` (`member_id` nulo = família; se preenchido, `auth.uid()`); `PATCH /goals/{id}`; `DELETE /goals/{id}` (só criador).
- `GET /goals/{id}/contributions`; `POST /goals/{id}/contributions` `{valor,data?}`.
- Shapes: `{id,titulo,valor_alvo,prazo,status,descricao,member_id,member_nome,criado_por,criado_por_nome,progresso,contribuicoes:[{id,member_id,member_nome,valor,data}]}`; membro inativo → `member_nome=null`.

### Previsão

- `GET /forecast?meses=12&escopo=familia|pessoal` → `{meses:[{mes,receitas,despesas,saldo,recorrentes_receitas,recorrentes_despesas,variavel_receitas,variavel_despesas,detalhes?}],anual:{...}}`.
- `escopo=familia`: RPC `family_forecast(p_family_id, p_mes_inicio)`; `p_mes_inicio` = primeiro dia do mês seguinte ao corrente; 12 linhas; sem membro/descrição; detalhes só agregados.
- `escopo=pessoal`: backend sobre os dados do próprio usuário, com detalhes por categoria/descrição.
- Fórmula: recorrentes ativos com confirmação nos 6 meses anteriores inclusive; último `valor_confirmado` (ordem `mes_referencia desc, confirmado_em desc`) ou valor da regra; média de 3 meses completos anteriores ao mês corrente; mês corrente parcial fora.

### Jev AI

- `GET /ai/messages?escopo=`; `POST /ai/messages` `{content,escopo}` → grava user/assistant, gera sugestões, devolve `{messages,suggestions,mode}`.
- `POST /ai/classify` `{descricao,tipo}` → `{categoria_id,categoria,mode}`; usa `classify(descricao,tipo,categorias)`; sem match `categoria_id=null`.
- `GET /ai/suggestions?escopo=`; `PATCH /ai/suggestions/{id}/read` `{lida:true}`.
- Geração: dashboard/summary/mensagem chamam `suggest(context)` quando não há sugestões recentes; upsert idempotente; `ai_suggestions` tem índice único de expressão; `23505` = já existe, ignorar.
- `AIContext`: `escopo`, `totais`, `categorias`, `media_3m`, `metas` (com `prazo`/`dias_para_prazo`), `transacoes` (só pessoal), `banco_pendentes`. Família sem `member_id`/descrição.
- Sem chave: fallback determinístico; toda sugestão tem `o_que`, `por_que`, `quanto` (ou “não é possível estimar”); modo `fallback`/`degraded` visível.

### Banco/Pluggy

- `GET/POST /banking/connections`; `DELETE /banking/connections/{id}` → Pluggy `DELETE /connections/{id}` se houver chave, depois `status='inativa'`; sem DELETE local.
- `GET /banking/accounts`; `GET /banking/transactions?connection_id=&status=&mes=`.
- `POST /banking/sync` `{connection_id}` → valida dono pelo JWT; service role insere `bank_connections`/`bank_accounts`/`bank_transactions`; nunca cria `transactions`; sem chave/service role → 503 ou no-op demo.
- `POST /banking/import` `{bank_transaction_id,category_id,escopo,valor?,data?,descricao?}` → `transactions` com `origem='pluggy'` e vínculo; trigger marca `importada`.
- `GET /banking/reconcile-candidates?bank_transaction_id=` → manuais com mesmo valor ±0,01, data ±1 dia, sem vínculo.
- `POST /banking/reconcile` `{bank_transaction_id,transaction_id}` → trigger marca `reconciliada`.
- `POST /banking/ignore` / `POST /banking/unignore` `{bank_transaction_id}` → status `ignorada`/`pendente_importacao`; demo: dono pode status, raw bloqueado.
- Sync lazy: ao abrir `/banking`, se `ultima_sync_em` > 24h ou nula, chamar `/sync`.

### Admin e demo

- `GET /admin/members`; `PATCH /admin/members/{id}` `{nome?,status?,tema?}` (RLS/trigger; admin não muda papel/tema de outro).
- `GET/POST/DELETE /admin/invites` (acima); `POST /invites/accept`.
- `GET/POST/PATCH/DELETE /categories` (padrão só oculta; personalizada do criador).
- `POST /demo/restore` → membro demo; DB URL; reexecuta `010`–`040` em uma transação; recria usuários/dados; sign out UX. O access token é autocontido: sessões/refresh são apagados, mas o access antigo pode valer até exp; documentar.
